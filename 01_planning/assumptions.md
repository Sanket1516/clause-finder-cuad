# Assumptions

Each assumption covers a point where the brief is unclear. It records the reason and how we would notice if it were wrong.
README §Assumptions will carry the reviewer-facing subset. Requirement IDs refer to the (git-ignored) requirements catalogue
(the requirements-to-code matrix was removed before publication).

| ID | Assumption | Why | Revisit if |
|---|---|---|---|
| A-01 | The submission repo is **private**, with collaborator access for the reviewers. | The logistics section says private, the deliverables section says public. Confidentiality favours private, and a private repo with collaborator access still satisfies "reviewers can clone it". | The candidate receives other instructions. |
| A-02 | "Character-level precision/recall as defined in the paper" means the authors' published code. Precision = overlap chars / **all** returned chars, *including chars from wrong documents*; recall = overlap chars / gold chars; a query with nothing returned scores P = 0, R = 0; scores are a macro-average over queries. | The dataset card wording ("in the right document") is ambiguous. `run_benchmark.py::QAResult` is unambiguous. | — |
| A-03 | Returned passages are made non-overlapping (per document) before scoring. Then the authors' sum-of-lengths formula and a set-of-characters formula agree. | The authors' code double-counts overlapping returns. With overlapping chunks that would inflate both precision and recall. | — (a test enforces the equality) |
| A-04 | Retrieval P/R@k is reported in two views. **Ranking view:** the ranked list before the abstention gate; comparable to the paper. **End-to-end view:** after abstention, where an abstained answerable query scores P = R = 0. | The brief asks for both retrieval quality and abstention. Mixing them in one number hides which component failed. | — |
| A-05 | k ∈ {1, 2, 4, 8, 16, 32, 64}, the authors' k grid. Several values are required; this grid keeps comparability. | The paper's grid. | — |
| A-06 | The leading `Consider "<title>";` clause of a query is legitimate inference-time input. Using it to route to a document (matching against corpus file names/text) is allowed. Gold `file_path` is never used. | It is part of the user's question text. Real users would also name the contract. | — |
| A-07 | Unanswerable queries use the same `Consider "<title>"; …` surface form as the benchmark. | If unanswerables are stylistically different, abstention would look artificially good (it would learn style, not relevance). | — |
| A-08 | "Indexed contracts don't answer it" is established by a documented **manual check** of the target contract, per query (keyword search + reading the relevant sections). Absence from `cuad.json` is *not* used as proof. | CUAD keeps only quotes that occur exactly once. A missing CUAD label does not prove a missing clause. | A later reviewer finds an answering clause. In that case we **do not edit** the frozen file; we record the defect in the report. |
| A-09 | Unanswerable mix (target ≥40, to get ≈12 in test): (a) indexed contract + clause type absent; (b) a contract *not* in the index; (c) a contract-like question the documents structurally can't answer (e.g. a business fact outside the contract). | It covers the brief's "questions about contracts that aren't in the corpus" and gives a usable test count. | — |
| A-10 | Benchmark queries are always answerable. An abstention on any of the 194 counts as a false abstention. | The dataset card states every question has ≥1 gold span. | — |
| A-11 | Duplicate query strings in the mini set (if any) are kept as separate items. They land in the same split automatically, because the split hashes the query text. | Fidelity to the authors' selection. | We count them in the manifest. |
| A-12 | The split is per query, not per document. The same contract can appear in train and test queries, so test measures generalisation to new *questions*, not new *contracts*. | Mandated split function. | Discussed in REPORT §Limitations. |
| A-13 | One CUAD `file_path` is NFD-normalised while its filename is NFC. Paths are matched with NFC normalisation on both sides; offsets are unaffected. | Dataset card. | Validation report shows otherwise. |
| A-14 | No LLM in the default pipeline. Any optional LLM must be **local** (e.g. via Ollama) to keep contract text on-machine; hosted APIs are excluded unless the user explicitly authorises them. | Privacy constraints; time budget; the brief says LLMs are optional. | User authorises a hosted model. |
| A-15 | Local open-weight embedding/reranker models downloaded from Hugging Face are acceptable. They run on CPU locally, so no contract text leaves the machine. | Privacy + no GPU available. | — |
| A-16 | "Test run" = any execution that computes metrics on a test-split query (benchmark or unanswerable). Every such run is appended to a ledger and counted in the REPORT. | The brief asks how many times test was run. | — |
| A-17 | REPORT.md and README.md live at the repo root. The numbered folders hold supporting material. | Reviewers expect them at the root. | — |
| A-18 | The submission repo is this directory's git repo, with the PDF and `00_assessment/` git-ignored. The PDF stays physically where it was found (originals must not be moved). | The brief prohibits including it in the repo; we must not move inputs. | The user prefers a separate clean repo directory (open decision D-OPEN-1). |
